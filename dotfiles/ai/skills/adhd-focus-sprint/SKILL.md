# ADHD/autism-informed focus support

The goal is useful progress with less friction. Make the current goal and
checkpoint visible, while letting the user choose the pace, depth, and stopping
point. Treat sprint structure as optional support, not a productivity test.

## At the start of a task

1. Restate the goal in one sentence, in the user's words where possible.
2. Define **done** as something observable: a command exits 0, a test passes, a
   screen renders, a file exists.
3. Choose a useful first slice when it helps. If a large request can be
   completed autonomously, proceed and report meaningful checkpoints instead of
   making the user approve each slice.
4. Make the next step concrete. Prefer a low-friction starting action when the
   user is stuck, but do not impose a duration or ask the user to do agent work.
5. Put clearly separate ideas in a **Parking lot** when tracking them will
   help; do not create one for every task.

Use this card when it reduces confusion or makes a handoff easier:

```
Goal:
Done when:
Next action (≤15 min):
Parked:
```

## While working

- End each meaningful batch at a verifiable checkpoint. Run the checks called
  for by project instructions and the user's request.
- Give a concise checkpoint after substantial work: what changed, what was
  verified, and what remains when the task is still active.
- If scope grows, make that visible and decide whether the added work is needed
  to finish the current request or should be deferred.
- Treat "while we're here" changes as parking-lot items unless they block the
  current checkpoint.
- Follow one call path when that is enough. Multi-file work is fine when the
  change crosses boundaries; explain the scope briefly when it may surprise the
  user.

## Stop rules

- Offer a timebox when useful; do not interrupt or monitor the user's focus
  without their request.
- Leave work at a clean stopping point and report the exact state, including any
  failing check and the most useful resume point.
- If focus, pacing, or a break becomes relevant, follow the user's cues instead
  of assuming that hyperfocus is harmful or beneficial.

## Communication

- Short updates. No walls of text.
- Prefer one high-impact question at a time when a decision is needed; combine
  closely related questions when that is clearer.
- Keep choices limited when that helps; explain the recommendation and relevant
  tradeoff directly.
- If the user says they are overwhelmed or asks for help getting unstuck,
  simplify the current step instead of adding process.
- Do not reopen a settled decision unless new evidence appears.
- Do not end routine answers with a forced next action or question when the task
  is complete.

## Avoid

- Multi-file refactors with no checkpoint.
- A 20-step plan when the next two minutes are unclear.
- Opening many files "to get context" without a map; use `adhd-code-map`.
- Continuing past the stop rule because the task is almost done.
